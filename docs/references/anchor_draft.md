# 锚点系统：历史讨论稿

> **这是一份历史工作稿，不是规范。**
> 当前设计共识以 [Anchors 布局设计](anchors.md) 为准；本文中的旧 API 草图、建议和待决问题
> 可能已被后续讨论修正。冲突时不要依据本文实现。
> 本文保留问题脉络、源码核实与讨论过程，供回看设计缘由。
>
> 状态：作者模型已有共识，具体实现细节仍待验证；本文的 Q1–Q7 状态已过期。

## 0. 一句话

项目现在只有一套定位系统（layout），因此**树的形状就是 UI 的形状**。锚点要补的是第二套
范式：空间关系由"谁贴着谁"表达，于是树可以是扁平的。设计在 §2 已经完整落定，
但**没有任何落地计划**，而且有两个规范空白和一处基类冲突必须先解决。

---

## 1. 问题：为什么需要它

### 1.1 起点不是"想要锚点"，是一轮使用反馈

[007](../../stories/007-two-designs-corrected-by-the-user-view.md) 起因是六条抱怨加一条
"想给文字加下划线但很难做"。七条里**五条指向同一个东西：节点的可定位 / 可动画表面太窄**。
锚点是这个判断在"定位"一侧的结论。

### 1.2 真正的驱动用例：侧边栏要在左在右

作者的原话（007 第四节）：

> 对**设计者**来说 anchor 是"给子组件外挂父属性"的工具，但对**开发者**这就是另一个
> 布局系统。只有 layout 时，开发者的思路是盒子模型层层包裹层层递进；有了 anchors 就不是。
> 侧边栏可以缩放、可以从左侧移到右侧，用 anchor 很简单（改锚点），用 layout 就麻烦一点。

以及那句定性：

> **QML 是以 anchor 为主、layout 为辅的。**

我最初的判断是"锚点是给个别子项钉位置的后门"——**那是设计者视角，错了**。验收用例
（§8 的 markdown 编辑器）就是用来钉死这一点的：它检验的是"**树 ≠ 布局**"能不能成立，
而不是"某个子项能不能钉住"。

### 1.3 一个容易混淆的同名物

`component_roadmap.md` 阶段 1 里的 **`AnchoredPositioner`（已完成）与本文无关**：它是
**浮层**定位器（placement / alignment / offset / flip / shift），服务于 Popover / Tooltip /
DropdownMenu 贴在触发控件旁的需求。本文说的锚点是**场景树里的节点定位范式**。
两者共用一个"anchor"词，讨论时要指明是哪一个。

## 3. 讨论过程：两次纠正与一次澄清

留在这里的原因是：**这三条决定了后面所有取舍的价值标准**。

### 3.1 第一次纠正 —— 锚点不是装饰

我把 anchors 定位成"layout 的补充"：挂在子项上的属性包，规则是"锚定的子项脱离排列流"。
作者指出这是把**另一个布局系统**降级成了装饰。修正结果：

- 从"补充"改为**对等系统、anchor 为主**；
- 从"个别子项钉位置"改为**一整套范式**（树≠布局的后果全部展开：显式 z 序、兄弟锚定、
  逐层治理都由此推出）；
- **兄弟锚定从"非目标"改成 v1 必需** —— 没有 `editor.left = sidebar.right` 就表达不出
  "内容区占掉剩下的空间"，而那是核心用法不是边角。

### 3.2 第二次纠正 —— `requires` 说不清"该填什么"

同一轮里我把 handler 的 DX 问题判成"用 `static_assert` / `requires` 把约束说清楚"。
作者指出：概念只能告诉使用者**哪里错了**，不能告诉他**该填什么**；而且使用者不知道
`Handler` 是什么东西。

这条与锚点无关，但产出了本轮通用的审核问题，对锚点同样适用：

> **这个改动的价值，是按"我多容易加进去"算的，还是按"它会怎么改变使用者写代码的方式"算的？**

### 3.3 一次澄清 —— 混用不是"报错"而已

我把"同层混用"记成了"会报错"。实际现状是**两个方向都静默失效**：

- 在 `Row` / `Column` / `Grid` 的子项上设锚点 → 锚点被忽略；
- 给已锚定的节点用排列属性（`Expanded`、`width(fill)` …）→ 排列属性被忽略。

而且**逐层治理是允许的**：可以用锚点摆一个 `Row` 的位置，再在 `Row` 内部用排列摆子项。
"混用"指的是**同一层**，不是"锚点和排列不能共存于一棵树"。

之所以要改成报错：本项目已被同一类失败咬过多次（配方 `apply_rule` 漏写、20 份
`same_text_style`、`activate` 永远非空、侧边栏那对死信号、`guarded()` 的假保护）。
**"设置成功但永远不生效"在这里是最坏的选项。**

## 4. 现状核实（代码层面）

写计划前必须知道插点在哪。以下是仓库实际状态：

### 4.1 锚点代码为零

全仓搜 `AnchorSpec` / `anchors(` / `anchor_to` / `clear_anchors`：无匹配。设计文档是唯一载体。

### 4.2 定位的插入点是 `layout_to(rect)`

`NanControl::layout_to(rect)` 是**全框架唯一的"这是你的矩形"汇点**，所有排列者都调用它：
`scene_tree`（根）、`Row`/`Column`/`Grid`、`card`、`scroll_view`、`pointer_area`、
`router_outlet`、`overlay_host`、`declarative`。

```text
SceneTree ──layout_to──▶ root ──on_layout──▶ child->layout_to(rect) ──on_layout──▶ …
```

**含义**：锚点求解器只要解出矩形并调用 `layout_to`，下游（裁剪、命中、语义、绘制、
主题）**一行都不用改**。这是本草案里最省力的一条结论，见 §5 R1。

### 4.3 但基类默认的 `on_layout` **本身就在排列**

`NanControl::on_layout()` 的默认实现是一条真实策略：

- 恰好 1 个可见子项 → 用 tight 约束让它**铺满自己**；
- 多个子项 → 每个按自身上限 measure，然后**保持 position、只更新尺寸**。

而 `nandina/widget/` 下有 **60 个类**继承 `NanControl`，其中**只有 18 处覆写了 `on_layout`**
（分布在 10 个文件里）—— 也就是说 **42 个类直接吃这个默认实现**。

**含义**：不能把"非排列容器默认就是锚定画布"当成自然推论 —— 那会**改掉 42 个类的现有行为**。
这是本草案最重要的发现，直接决定了 §5 R2 和 §6 Q1。

### 4.4 L2 已经把底座铺好了

刚落地的表现层变换把 `layout/base transform` 与 `presentation transform` 分开了
（§5.0 ③、§5.1），所以锚点**只需要产出 layout rect**，`translate` / `scale` 会自动叠在上面。
不需要为了锚点再动表现层。

## 5. 建议

四条，按重要性排序。前两条是"动手前必须接受的前提"。

### R1 锚点求解器 = 第三种排列者，只做一件事

它不碰绘制、不碰命中、不碰语义，只回答"这个子项的矩形是什么"，然后 `layout_to`。

```text
排列容器：on_layout() 决定子项矩形        （已有）
锚定画布：on_layout() 跑锚点求解器        （新增，同样以 layout_to 收尾）
```

好处：下游契约零改动；`overflow` / 命中 / 语义 bounds / z 序全部沿用现有实现；
出问题时排查范围和排列容器完全一样。

### R2 画布必须**显式声明**，不能靠"非排列容器默认就是画布"

理由就是 §4.3：基类默认已经在排列，42 个类依赖它。把它改成锚定画布是**破坏性**的，
而且会顺手破坏 §2.2.1 想要的报错——"谁在排列"将不再可判定。

建议形状（具体命名待定）：给 `NanControl` 加一个"**这一层用哪套**"的虚查询，
`Row` / `Column` / `Grid` 声明为**排列**，显式画布声明为**锚定**，其余默认值**保持现状**
（维持兼容，也维持现有默认排列行为）。挂载时的父子冲突检测直接查这个查询，两侧信息都已知。

**这一条同时解掉 Q2**：如果"在锚定画布里用排列属性"能报错，就不必再规定
`Expanded` "什么也不做"。

### R3 落地顺序（每步都带"改坏哪里会红"）

```text
0. 拍板：Q1（画布声明）、Q2（Expanded）、Q3（跨容器）、Q4（reparent）、Q5（裁剪交叉）
   —— 这五条会改 API 形状或已有契约，未定不要开工
1. 数据模型：AnchorSpec / Anchor + 节点上的锚点存储 + 设置时的同轴冲突拒绝
   （§2.7 表的前两行；此时还没有求解器，"设置就报错"可以先独立成立）
2. 画布声明 + 挂载时父子冲突报错（§2.2.1 第二级）+ clear_anchors()
3. 求解器：隐式尺寸 → 依赖序 → 环检测（§2.3）。先只支持父边锚定
4. 兄弟锚定（§2.4）+ 环检测覆盖兄弟环
5. z 序（§2.5）：绘制与命中同序
6. 验收：§8 的 markdown 编辑器四条 + 下划线冒烟；锚点结果对重复布局的抵抗
```

第 1、2 步可以独立交付且有价值（**报错本身是行为改变，会立刻暴露现有误用**），
不必等求解器。第 3 步之前不要写任何 anchor 的公开 DSL —— 否则"设置成功但不生效"会重演。

### R4 第一刀切窄

v1 只做：**扁平原生画布 + 四边（left/right/top/bottom）+ 兄弟锚定 + 环检测 + 两级报错**。
`horizontal_center` / `vertical_center`、`Anchor::margin` 的完整语义、滚动联动、
`rotation`（已是非目标）都往后放。理由：中心线与环检测、依赖序会互相影响，
先让"左边贴左边、右边贴兄弟左边"这条主干端到端跑通。

## 6. 待决问题

每条给：背景 / 影响 / 我的倾向。**Q1–Q5 建议在动代码前拍板。**

### Q1 画布怎么声明？（对应 R2）

- 背景：§4.3 —— 基类默认已在排列，42 个类依赖它。
- 影响：决定 `NanControl` 是否新增虚函数、决定挂载时报错的判定依据、决定是否破坏兼容。
- 倾向：**显式声明 + 默认值维持现状**。不采纳"非排列容器即画布"。

### Q2 `Expanded` 在锚定画布里到底是什么？

- 背景：**§2.8 与 §2.2.1 互相矛盾**。§2.8 说它在锚定画布里"什么也不做，就是一个固定尺寸
  的占位盒子"；§2.2.1 说"排列属性在锚定语境里被忽略"这件事**要改成报错**。
  而"什么也不做"正是 §2.2.1 要消灭的那个失败模式（作者写了 `Expanded` 却没推开，
  看起来和 bug 一样）。
- 影响：决定是不是又多一条静默失效路径，也决定 §2.8 那段要不要重写。
- 倾向：**报错**（与 §2.2.1 一致）。若坚持保留"固定尺寸盒子"的读法，必须同时说明
  "它在锚定画布里没有位置，需要自己给锚点才可见"——否则两种读法都通。

### Q3 能锚到谁？

- 背景：§2.6 说了"目标为 `nullptr` = 父容器；指向兄弟"。但没说**能不能锚到别的容器里的节点**。
- 影响：环检测的范围、依赖序是否跨子树、以及"锚到已滚动出去的兄弟"这类情形。
- 倾向：**只允许同一父容器下的兄弟 + 父容器本身，跨容器锚定明确禁止并报错**。
  否则依赖序要跨子树，环检测与隐式尺寸的边界都说不清。

### Q4 重新挂载（reparent）时锚点怎么办？

- 背景：锚点用指针指向兄弟（§2.6）。挂载到新父容器后，目标可能不再是兄弟、甚至已销毁。
- 影响：`add_child` / `insert_child` / 完整 detach 的现有语义要加一条。
- 倾向：**重新挂载时校验，失效则报错**（不静默清空 —— 静默清空会让 UI 悄悄走形）。
  名字兜底（§2.6）的解析时机也在这一条里定。

### Q5 锚点 × 裁剪与滚动

- 背景：`overflow_and_clip.md` 定义了裁剪契约，`scene_tree` 的裁剪用 `global_bounds()`。
  被贴的兄弟如果被裁剪 / 在 `ScrollView` 里滚动了，锚点跟不跟？
- 影响：要改的是**已有契约文档**，不是新文档。
- 倾向：v1 明确写成"**锚点解的是布局矩形，不跟随裁剪与滚动**"，并把交叉情形列为已知边界。
  等真的遇到滚动画布再设计。

### Q6 画布自身的隐式尺寸怎么算？

- 背景：§2.3 第 1 步说"每个节点先解出自己的隐式尺寸（内容 / 显式宽度 / 排列结果）"，
  但对**锚定画布**没定义：内容并集？最大子项？还是必须有显式尺寸？
- 影响：决定"画布能不能由内容撑开"，也决定 §8 验收第 2 条（侧边栏宽度由内容隐式决定）
  里"谁在撑谁"。
- 倾向：**画布默认必须有显式尺寸（或由父层锚定拉伸）**，内容不撑开画布；
  需要"内容撑开"时用"子项锚定 + 画布隐式尺寸 = 子项并集"作为显式选项。

### Q7 锚点在路线图里排第几？

- 背景：`component_roadmap.md` 完全没有布局基础设施这一项（它的 "anchor" 全是浮层定位器）。
- 影响：这是产品判断，我不该替你排。
- 我能提供的**依赖关系**（不含优先级）：与"调度侧 DSL"（node_presentation §6.1）**互不依赖，
  可并行**；与"形状家族"（§3）**弱依赖** —— §8 的下划线冒烟需要公开 painter 入口，
  但那不是锚点的前置。与"盒子模型"（§4）**无关**：`padding` / `margin` 是流内概念，
  `Anchor::margin` 是"距目标边的距离"，两者不是同一个 margin。

## 7. 验收与验证计划

### 7.1 功能验收

用 [§8](node_presentation.md) 的四条（侧边栏换边只改锚点、隐式宽度 + 剩余空间、
侧边栏内部排列不受外层影响、写错锚点确定性报错）+ 下划线冒烟。**不在这里重复。**

### 7.2 锚点专属的"改坏哪里会红"清单

按 [开发流程](development_loop.md) 第 3 节的要求，每条都要能说出改坏哪一行会让它失败：

| 测试 | 改坏什么会让它红 |
| --- | --- |
| 同节点同轴冲突 | 去掉设置时的互斥检查 → 静默接受 `left+right+width` |
| 父子语境冲突 | 去掉挂载时校验 → 锚点被排列静默覆盖（§2.2.1 那个失败模式） |
| 锚点环 | 去掉环检测 → 死循环或未定义结果 |
| 兄弟锚定 + 剩余空间 | 去掉依赖序 → 求解顺序错，宽度算成上一轮的值 |
| 隐式尺寸 + 锚定 | 去掉"先隐式尺寸"这一步 → 内容撑不开或撑错 |
| z 序：绘制与命中同序 | 只改绘制不改命中 → 点到了看不见的节点 |
| 布局抵抗 | 让锚点结果写进表现层而不是 layout → 下一次排列把它抹掉（§5.0 ③ 的老坑） |
| reparent（Q4 定案后） | 去掉重挂载校验 → 锚点指向非兄弟，行为未定义 |

### 7.3 一个反例测试值得专门写

**"锚定画布里的排列属性必须报错"** —— 这条同时锁住 §2.2.1 的第二级报错和 Q2 的答案。

## 8. 风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **破坏现有默认行为** | 基类默认 `on_layout` 已在排列，42 个类依赖它 | R2：显式声明，默认值不动 |
| **契约扩散** | 裁剪、命中、语义、滚动四份契约都要提"锚点怎么算" | R1：只产出 layout rect，让下游复用 |
| **两个工具干同一件事** | 锚点 / `Expanded` / `width(fill)` 都能表达"占满剩余" | §2.8 收窄 `Expanded`；`fill` 明确用四边表达；Q2 定案 |
| **"设置成功但不生效"重演** | 锚点被排列覆盖、锚点被裁剪截断 | 两级报错 + 7.2 的清单 |
| **隐式尺寸与锚点互相依赖** | "左边贴左、右边贴右"时宽度由锚点决定，不该再依赖内容 | §2.3 的求解顺序要写成明确规则：锚点定死的轴**不参与**隐式尺寸 |
