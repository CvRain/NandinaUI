## 1. 目标：统一交互语义，不按设备开关焦点环

注册表单应允许用户混合使用鼠标、触摸、笔、键盘和手柄，而不要求组件各自识别设备。
设备来源是上下文，交互意图才是行为入口：

| 交互方式 | 如何确定目标 | 例子 |
| --- | --- | --- |
| 指向定位 | 坐标与命中测试确定目标 | 鼠标点击、触摸点选、笔点选、手柄模拟指针 |
| 焦点导航 | 框架按顺序或方向选择目标 | Tab / Shift+Tab、手柄方向导航 |
| 编辑输入 | 向既定编辑目标输入或修改内容 | 文本提交、输入法组合、光标移动、选区操作 |

同一设备可以产生不同意图，不能把手柄、触屏或数位板永久绑定到某一种策略。
统一事件仍需保留来源；后续指针适配还要表达接触点身份、取消等语义，不能只把触摸伪装成鼠标。

本设计不要求同时实现所有设备、所有平台，也不以更换 raylib 为前提。

## 2. 四个职责与唯一事实来源

| 职责 | 回答的问题 | 归属与约束 |
| --- | --- | --- |
| 输入归一化 | 发生的是指向、导航、激活还是编辑？ | 平台适配产生框架事件；scene 不依赖设备 SDK |
| 焦点管理 | 谁接收输入、能否转移、在哪个范围内？ | scene，复用 NanSceneTree 与已有 focus scope / 浮层规则 |
| 焦点呈现策略 | 是否必须清楚标出当前输入目标？ | scene 统一决策，widget/theme 负责表现 |
| 文本输入会话 | 谁接收组合/提交文本，是否请求软键盘？ | 编辑目标协议 + 应用/平台服务；不得通过具体 widget 类型反向依赖 |

树内输入焦点的事实来源仍是现有焦点管理，不在每个组件或新服务里再维护第二份可独立修改的目标。
输入来源与交互方式按窗口/场景上下文隔离，不用跨窗口的全局 `last_device`。
软键盘实际是否可见属于平台反馈，不是焦点状态的别名。

目标语义查询统一命名为（具体声明位置与签名仍待实现前定形）：

```cpp
focused()                 // 是否拥有输入焦点：输入分发与 semantics 使用这一事实。
should_show_focus_hint()   // 是否应呈现焦点提示：只读策略查询，不保证一定画“环”。
```

该查询取代讨论中的 `focus_visible()` 拼写，避免与 `visible()` / `is_visible_in_tree()` 混淆；
它不提供任意 setter，不是另一份焦点状态。隐藏提示不取消焦点，不改变导航资格，
也不把语义树中的 focused 改成 false。反过来，selected / current / pressed 不能冒充输入焦点。

## 3. 默认呈现策略

以下是 Nandina 的目标行为，不宣称完整复制浏览器或任何操作系统的启发式算法。

| 操作 | 普通按钮 | 可编辑输入框 |
| --- | --- | --- |
| 鼠标点击 | 保留按压反馈，通常不持续显示焦点提示 | 显示明确的编辑焦点提示 |
| 触摸或笔点选 | 按指向定位处理，通常不持续显示提示 | 显示编辑焦点提示；软键盘由会话策略决定 |
| Tab / Shift+Tab | 显示导航焦点提示 | 显示焦点提示，允许硬件键盘输入 |
| 手柄方向导航 | 显示导航焦点提示 | 显示目标；确认进入编辑的流程由会话策略处理 |
| 程序化聚焦 / 焦点恢复 | 使用 §4.2 的明确上下文、最近有意义交互与无历史默认值 | 先满足目标提示需求；编辑会话与软键盘另行决定 |

必须支持的原则：

- 用户“始终显示焦点提示”的偏好优先于默认的指向隐藏策略。
- “需要提示”不等于“所有控件额外画同一种环”。主题可用边框、背景或外环表达，但必须清楚标出目标。
- 文本输入控件是独立的能力类别，不能套用“鼠标聚焦一律不显示”的规则。
- scene 通过低层能力/策略协议了解目标需求，不通过识别 TextField / TextArea 的具体类型判断。
- 第一阶段不增加通用 `.focus_ring(false)` 逃生门。若后续确有等价提示或委托焦点需求，
  先定义与用户偏好、主题覆盖的优先级；不能用关闭绘制替代交互设计。
- 只改变提示状态，不应引起组件重排；绘制必须消费统一结果，而非各自读取设备状态。

### 3.1 文本能力矩阵（阶段一输入）

下表是目标能力组合，不表示现有 Label 已增加文本选择等功能。策略通过能力协议判断，
不能仅凭“名字里有 Text”决定可聚焦性或编辑会话；只读不等于不可聚焦。

| 能力 | 焦点提示默认值（窗口活动且目标持有焦点时） | 文本输入会话 |
| --- | --- | --- |
| 可编辑字段 | 显示明确编辑提示，包括指向聚焦 | 可建立，软键盘另行决策 |
| 只读、支持键盘选择/复制的字段 | 显示明确提示，包括指向聚焦 | 不因聚焦启动编辑或请求软键盘 |
| 可选择的展示文本 | 支持键盘选择/复制时采用上行规则；仅有指向选择能力不自动加入 Tab 序列 | 不启动编辑 |
| 普通不可交互 Label | 默认不进入焦点序列，无输入焦点提示 | 不建立 |

disabled 等现有可聚焦性约束先行生效；能力矩阵不允许绕过它们为无效目标显示焦点提示。

### 3.2 纯提示变化的标脏规则

策略上下文归 scene 的 tree/window 范围。焦点目标及语义状态均不变，仅**有效提示结果**改变时，
由 scene 发起受影响绘制位置的 `DirtyFlags::paint` 失效，不新增 measure、layout、transform
或 semantics 脏标记，不全树广播。普通控件标当前焦点节点；委托绘制/内部活动项模型见 §4.3，
不能把“永远只标真实焦点节点”写死为通用约束。

- 策略上下文变了但提示结果未变，不必仅因上下文变化标 paint；例如可编辑字段从键盘切到鼠标仍需提示。
- 不清除先前已有的任何脏标记；真正的焦点转移仍须更新旧/新目标、提示和语义，不适用 paint-only。
- 状态变更应在对应绘制读取之前可见；不能只在 focus-enter/leave 中缓存提示而漏掉同节点变化。
- 测试先清理相关节点脏标记、刷新语义快照建立基线，再断言 paint 为真，measure/layout/transform/
  semantics 未新增。还须断言树级语义更新未重建快照、revision 不变且 focused 仍为真：
  仅查节点 semantics 位抓不住树的 `mark_semantics_dirty()` 被误调用。
- 补一条已有脏标记不被清除的测试；paint-only 描述本次操作的增量，不描述操作后全部状态。

当前窗口无条件重绘，paint 位尚未成为生产绘制开关（见 [节点表现层 §5.1](node_presentation.md)）。
这是当前的失效契约，也是后续门控重绘的前提；未来接门控时仍需验证委托绘制和旧提示的擦除范围。

## 4. 变化过程比设备枚举更重要

### 4.1 焦点不变，提示仍可能变化

同一个按钮先被指向点击、后接受键盘操作，策略也必须重新计算。
不能只在 focus-enter / focus-leave 时刷新提示，更不能因目标指针相同而跳过一切更新。
有意义的导航、激活与编辑动作参与策略；哪些原始按键属于这些动作，应在事件映射层集中定义。

鼠标轻微移动、笔悬停等被动事件不得直接抹掉键盘导航提示。记录的是有意义的交互，
不是“最后收到哪个底层事件”。失败的聚焦请求不得产生虚假的焦点转移。

#### 阶段一默认事件映射

| 原始事件 | 上下文与处理规则 |
| --- | --- |
| 鼠标按下 | 指向交互；在处理可能产生聚焦的回调前建立上下文；不据此无条件激活控件 |
| 鼠标释放 | 完成既有按压/取消流程，不独立切换提示策略 |
| 鼠标移动、悬停、滚轮 | 不改变提示策略；滚动/调值等自身行为仍可产生其他失效 |
| Tab / Shift+Tab | 顺序导航意图，遵守组件消费与作用域规则 |
| 方向键、Home/End、PageUp/PageDown | 建立键盘操作上下文；编辑、调值或导航由消费者决定 |
| Enter / Space | 建立键盘操作上下文；按目标解释为激活、编辑或其他操作，不统一强制激活 |
| Escape | 键盘取消/关闭上下文，供随后焦点恢复使用 |
| Backspace/Delete、目标支持的编辑快捷键 | 编辑或组件操作，不转换为全局导航 |
| 单独修饰键 | 不切换提示策略 |
| 已提交文本 | 交给当前编辑目标或组件的 typeahead 等语义；不据此推断硬件键盘或改写成硬件键盘模态 |
| 组合更新 | 按文本会话处理，不据此推断硬件键盘；当前没有生产入口，属于第二阶段验收 |
| 窗口失活/激活 | 生命周期事件，不改写最近有意义交互，规则见 §4.5 |

此表区分“建立上下文”与“执行导航”：前者须让回调内的焦点请求读到此次交互，后者必须给组件
先消费的机会，不能先换焦点再询问组件。有效快捷键由目标支持的命令映射判定，不能将任意带
Ctrl/Alt/Meta 的按键都当导航；其他未识别按键默认不切换策略，也不妨碍原有事件分发。
提交文本和组合更新不创建第二套全局模态；目标如将文本解释为 typeahead，仍走其活动项更新路径。

### 4.2 程序化转移必须有原因

焦点请求需要区分指向定位、导航、程序化跳转、弹窗进入、恢复以及辅助技术请求等原因。
**转移原因**说明“为什么转移”，**交互上下文**说明本次操作属于指向还是键盘/导航；
`restore` 本身不能决定提示是否显示。具体枚举和参数类型待第一阶段定形，默认行为现在明确：

1. **先经过前置门槛**：目标无效或窗口失活时不显示活动焦点提示（见 §4.5，优先级高于“始终显示”）；此判断不负责清除仍合法的逻辑焦点。
2. 窗口活动且目标有效时，用户“始终显示”和目标的必需提示能力优先于默认隐藏策略。
3. 无上述强制显示需求时，使用此次请求明确携带的交互上下文。
4. 未携带时，沿用当前窗口最近一次有意义交互的策略，不读取全局最近设备。
5. 尚无交互历史时默认显示，避免首次程序化聚焦完全不可见；保留 unknown/无来源的语义，不伪装成 pointer。

上述顺序只决定提示；不隐式启动编辑会话或请求软键盘，也不为暂定默认值引入一次性过渡 API。

**无历史默认显示是明确接受的取舍，不是忘记处理第一帧。** 非可编辑按钮启动时自动聚焦可能
让鼠标用户看到提示，但用户第一次操作也可能是 Enter/Space，而不是 Tab。若默认隐藏，
即使在按键分发前更新提示，激活也可能在同一轮完成，无法保证用户在操作前已经看到目标。
语义 focused 为真只证明焦点事实一致，不能单独证明视觉使用者或辅助技术用户没有体验损失。

当前 `FocusScope::on_ready()` 和 `NanRouter::restore_focus_after_navigation()` 已有无须先发生
输入的聚焦路径，因此必须测试挂载后、首次输入前的状态；不能假定启动自动聚焦只是未来需求。
页面是否应该自动聚焦第一个动作按钮，是单独的产品/路由策略问题；本轮不改变该行为，
不靠隐藏提示掩盖它。明确的键盘流程仍须携带上下文，默认显示不能替代正确传递原因。

进入弹窗、关闭弹窗恢复触发者、校验失败定位字段，需要携带足够上下文。
恢复目标已销毁、隐藏或不可聚焦时，应遵守现有作用域与可聚焦性规则，不恢复到悬空节点。
恢复不得机械复制打开时的提示：**鼠标打开弹窗、Escape 关闭后，触发按钮恢复焦点时显示键盘提示**。
Escape 的上下文必须在关闭/恢复回调前生效；已有“始终显示”及目标能力优先级不变。

### 4.3 导航不能抢走组件操作

文本光标移动、Slider 调值、菜单漫游先按组件自己的语义消费事件；未消费的导航请求
才交给相应焦点范围处理。不能把所有方向键或手柄方向输入无条件变成“换一个控件”。
复用既有 focus scope、模态限制和 roving focus，不另造一套手柄专用焦点树。
二维方向导航的候选排序属于第三阶段设计，不在本轮偷偷选一个几何算法。

第一阶段分别验收两种既有 roving 模型，不借 D1 重构全部焦点所有权：

- **成员持有真实焦点**：RadioGroup 使用 focus-and-selection，真实焦点移到 RadioButton；
  提示与语义必须跟随相应成员。
- **容器持有真实焦点、内部活动项漫游**：Tabs 和 DropdownMenu 已使用 selection-only 路径。
  提示应清楚标出当前可操作项，与既有 active/selected 状态一致，不能为了“子项必须 focused”
  强行转移真实焦点或另存一份活动项。

语义断言分别按控件既有模型验证，不把内部高亮统一改写成场景树焦点。委托到内部绘制节点时，
纯提示切换要覆盖这些绘制位置；活动项变化还要使旧/新提示位置失效。后者可能伴随 selection
或语义变化，不能误套 §3.2 的纯提示断言。两种模型都须验证方向事件只消费一次、无额外外层导航。

### 4.4 无障碍浏览不等于编辑焦点

辅助技术的对象浏览与显式 focus / activate action 保留语义区别。
不能将每次浏览都转换成 `set_focus()`，更不能因此自动请求键盘。
真实输入焦点及其语义快照必须保持一致；提示的显示策略不得破坏已有语义 action。

### 4.5 窗口失活与重新激活

第一阶段默认保留仍合法的逻辑焦点目标，但窗口失活期间暂停活动焦点提示；这不是清焦点，
也不是把“最近交互”改成 pointer。“始终显示”覆盖的是活动窗口内的模态隐藏，不覆盖窗口失活。
重新激活时验证目标与作用域并重新计算提示，不伪造导航或对同一目标重复发送 focus-enter。
目标在失活期间被移除/禁用等情况仍按现有合法性规则处理，不保留悬空引用。

窗口事件需要接入 scene；仅有测试中的模拟状态不足以声称真实窗口路径已验收。
第二阶段另测文本会话的暂停/结束、composition 处理与迟到事件隔离；具体平台的组合提交/取消
次序在会话协议定形时明确，不能由提示开关决定。重新激活不无条件弹出软键盘。

## 5. 文本输入会话与软键盘

三个状态必须分开：**得到焦点、进入编辑、平台键盘实际显示**。

```text
聚焦或激活请求
  ├─ 更新输入焦点
  ├─ 重新计算焦点提示
  └─ 若目标可编辑，按策略建立/更新文本输入会话
       └─ 按平台能力与请求上下文请求软键盘，并接收实际状态
```

不允许“显示焦点环 → 弹出键盘”的依赖。典型行为：

- 触摸可编辑字段可以请求进入编辑与软键盘；具体是否显示由平台决定。
- 硬件键盘 Tab 到字段允许直接输入，不由框架无条件强制弹出软键盘。
- 手柄导航到字段先显示目标，可以通过确认进入编辑并请求软键盘。
- 校验失败后程序化定位字段应使其可见；是否请求键盘由该次请求决定。
- 用户收起软键盘不必取消字段的逻辑焦点，也不应因随后的普通刷新立即强行重开。

第二阶段会话协议至少需要明确：

1. 开始、目标切换、结束与取消；composition 更新、提交及取消的次序，不把组合文本重复提交。
2. 输入用途（如密码、邮箱、数字）与可编辑性；不能对只读或已失效目标启动编辑。
3. caret / 输入区域的位置与坐标系，以及窗口缩放、滚动后位置的更新。
4. 软键盘显示请求、实际状态和遮挡区域；滚动避让与布局协作，不把平台遮挡硬编码成节点高度。
5. 页面销毁、节点离树、窗口失活时的清理；迟到事件不能写入已销毁或新的错误目标。
6. 能力查询与失败结果；平台缺失的功能必须可诊断，不“设置成功但无效果”。

公开协议不得暴露 raylib / SDL 等平台类型。平台实现选择不属于 D1 决策；
没有接通真实后端时，应标记“协议/模拟测试已完成”，不能声称设备或输入法已经支持。

真实平台验收的前提是**对应平台文本输入能力接通**，而非整个 D4 后端迁移完成。
能力来源可以是现有后端扩展、独立平台适配或 D4 新平台层；当前 app 没有组合事件通路，
不能据此推导只有更换后端一条路。没有接通能力时，该能力的交付上限仍是协议与模拟测试。
分别记录以下状态与具体平台，不用一个“阶段二完成”勾选框互相替代：

- 协议与模拟测试完成；
- 指定平台的组合输入已验证；
- 指定平台的软键盘请求、反馈及遮挡处理已验证。

### 5.1 注入式文本输入服务（已实施，P3.3a）

协议与 SDL 合成路径已落地在 `scene/text_input_service.hpp`、`NanSceneTree` 会话管理和
`app/detail/sdl_text_input_service`；P3.3b1 补齐视觉 preedit 与密码用途。以下保留接口定形时的
约束，便于后续 P3.3b2 的 caret 区域/软键盘适配复用同一服务边界。


沿用 `scene::IClipboard` 的平台中立、由窗口注入的服务形状。目标服务暂名 `ITextInputService`：
协议归 scene，具体平台实现及其资源由窗口持有或管理，场景管理编辑目标和会话。
实现不依赖具体 widget，公开值类型不出现 raylib/SDL 等 SDK 类型；后续协议如需共享值，应放在
实际依赖层，不能让 scene 反向引用 widget。精确方法签名和连接类型在第二阶段代码前确定。

- 窗口在服务可用后、首次编辑请求前注入；没有服务时，能力查询与请求应明确返回不可用/不支持。
- 现有后端扩展、独立平台适配和 D4 新后端都通过同一服务边界接入，不增设全局状态或具体平台旁路。
- 复用的是**注入方式**，不是剪贴板的同步生命周期假设。剪贴板的一次读写可以同步完成，
  文本服务还会回报延迟事件，单纯保存/清空一个裸指针不是完整安全协议。

请求与回报两条方向分别定义：

| 方向 | 语义 | 约束 |
| --- | --- | --- |
| scene → 平台服务 | 开始/更新/结束会话，更新输入区域，请求键盘显示或收起 | 请求目标通过会话标识关联，不让平台实现持有并直接修改 widget |
| 平台服务 → scene | 组合更新/取消、文本提交、键盘可见性与遮挡变化 | 通过生命周期受保护的事件入口回报；不得从平台回调任意线程直接修改场景树 |

**会话身份是必须项。** 使用会话身份/代次区分字段、重新建立的会话以及服务重新连接。
字段 A 结束后，A 的迟到组合/提交事件不能因为 B 当前获得焦点而被写入 B；即使新旧目标是同一
节点，也不能让旧会话事件进入新会话。已有的已提交文本通路在接入服务时应明确唯一投递路径，
避免新旧适配重复提交同一次输入。

**解绑需要显式次序。** 窗口关闭、服务替换或连接撤销时，先使旧会话/投递入口失效，再结束
平台会话并解除连接，最后释放实现。终止过程中产生的回调和已排队事件也必须被旧身份挡住；
只清空场景里的服务指针不能完成这一保证。输入事件在 UI 分发边界串行处理，具体线程转发与
终止时 composition 的提交/取消规则需在接口定形时明确，不由焦点提示策略决定。

### 5.2 能力、请求结果与验收记录不能互相替代

`supports()` 表达能力集合，不表达实现等级。组合输入、软键盘请求、可见性反馈、遮挡信息
等能力可以分别支持；同一实现可以覆盖多项，也可能只支持键盘请求却无法回报遮挡区域。

每次请求还需要可诊断结果，区分未支持、服务/会话不可用以及平台拒绝/失败等情况。
平台接受请求不等于键盘已显示；可见性未知也不能伪装成已隐藏，遮挡信息未知不能伪装成零遮挡。
状态查询/事件应能表达未知或不支持，具体结果类型在第二阶段定形。

模拟实现可以宣称并模拟多项能力，但它不能因此升级成平台验收证据。§5 的三项交付状态记录
“什么在何平台、用什么方式验证过”，不对应“协议桩/组合实现/键盘实现”三种固定服务类型。
能力查询属于运行时协议，验证记录属于交付证据，不把后者再做成一份全局运行时状态。
