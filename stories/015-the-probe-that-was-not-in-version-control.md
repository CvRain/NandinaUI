# 探针在版本控制之外待了两周，然后我们决定换掉生产后端

> 2026-10-15，D4 记录归档。**方向已定：先补齐 D4 计划内容，再把生产后端替换为 SDL3；
> 迁移尚未开始。** 正式契约见[平台与后端契约](../docs/references/platform_backend_contract.md)，
> 探测证据见[跨平台后端探测](../docs/references/cross_platform_backend_probe.md)，
> 源码与构建方式见 [probe/cross_platform/](../probe/cross_platform/README.md)。
> 本篇写的是过程，包括当时的错判。

## 一、它一直在被 git 忽略的目录里

探测是 2026-10-13 做的，落在 `playground/sdl_gpu_probe/`。那个目录被 `.gitignore` 整目录忽略，
理由是「可能会被随意修改」。于是「我们试过 SDL3」这句话只存在于一篇文档里，代码本身一次
`git clean` 就没了；1.8 GB 的 emsdk 和 build 目录也在那儿，所以当时很难说「把源码挑出来入库」
值不值得。

转折点是 P1 的门槛本身：它要求 **host 工具固定版本、产物进构建图、失败可定位**。这些都要求
探测是**可复跑的构建**，而不是一次性的产物。于是把四项源码（`desktop/`、`web/`、
`tools/verify_toolchain.sh`、`README.md`）挑进 `probe/cross_platform/`，emsdk、SDL 源码树和
build 目录继续现取现建。

挑出来的时候才发现两处**文档与事实不符**，都是我两周前写的：

- README 声称「`spirv-val --target-env vulkan1.0` 通过」，但 CMake 与 build.ninja 里都没有这一步。
  我当时确实手工跑过一次，然后把它写成了构建的一部分 —— 这正是「文档描述意图、代码是事实」
  的典型错位。现在它是构建图里的一步，并且实测有效：把 `generated/sdf.frag.spv` 换成垃圾数据，
  构建在 `spirv-val` 一步失败（`error: file size should be a multiple of 4`）。
- README 写「Emscripten 未安装」，但本机 `playground/sdl_gpu_probe/emsdk` 就是 6.0.10
  （d6c521a7）。写那句话时我还没建 emsdk，后来建了却没回头改文档。

## 二、先做几何设备，而不是把 SDF shader 搬过来

`IRenderDevice` 的探测记录里有一条前置条件：「让探测走一次真实的 `IRenderDevice`，这样测到的
才是框架行为，而不是另一个程序的渲染」。第一版实现我选了 SDL 2D API + **CPU 三角形扇**画圆角，
而不是把生产的 SDF shader 搬过来。理由有三条，事后看仍然成立：

1. 记录 §2 给 Web 定的暂定路线就是「CPU 几何/覆盖率 + 独立设备」，先做一遍等于验证那条路线；
2. 几何实现的差异是**能力差异**，正好能填出 §3 那张表；
3. 搬 shader 会把「契约能不能实现」和「shader 能不能编译」两个问题搅在一起。

过程中撞了一个可笑的坑：圆角矩形第一版用「整圈轮廓一次扇形三角化」，渲染出来是 **V 形**。
那种做法要求轮廓点严格凸且绕向一致，我四段圆弧的角度方向写反了一段。改成「中心矩形 + 左右
边条 + 四个各自凸的 90° 扇」之后不依赖任何隐式约定。我当时的第一反应是怀疑 `SDL_RenderGeometry`
的索引语义，差点去查文档 —— 其实是我的几何错了。

## 三、真实页面：三个小时里最花时间的是找 alpha 通道

手写图元只能证明「契约可实现」。真正回答记录里第二件事（用真实页面而不是 SDK 示例）的是
`page_probe.cpp`：`NanApplication` + `NanRouter` + `NanSceneTree` + 本设备组成最小宿主，挂载
**真实的 showcase `LabelPage`**。刻意不用 `NanWindow`，因为它同时持有窗口、设备、输入与帧驱动 ——
那正是 P4 要拆的东西，我不想在探测里把它当成绕不过去的前提。

第一版渲染出来：版式、卡片、颜色、裁剪全对，**文字全是黑色实心方块**。

找根因的顺序值得记下来，因为它避免了两次错误修改：

1. 先怀疑源矩形/目标矩形不对 → 打 trace，看到 `src=(0,0 16x22)` 这种小字形区域、目标 1:1，
   数据是对的；
2. 再怀疑图集上传的内容不对 → 统计上传区域：`nonzero=845/2040 peak=255`，是真实字形覆盖率；
3. 放大截图的标题区域，才看清是**反相**：每个字形四边形整体不透明，字形形状是「挖空」的。

所以问题在通道，不在几何。根因是 `SDL_PIXELFORMAT_RGBA8888` 是**打包**格式（`0xRRGGBBAA`），
小端机上的内存字节序是 `A,B,G,R`，而设备产出的是 `R,G,B,A` —— alpha 从错误的字节读出来，
恒为 255。改用平台首选的 `SDL_PIXELFORMAT_RGBA32` 即刻正确。同一轮还补上了
`SDL_SCALEMODE_NEAREST`：生产后端对字形图集用点采样，线性过滤会二次软化并让相邻图集条目渗色。

修完之后：真实页面 + 真实主题 + HarfBuzz 整形 + 真实 `GlyphAtlasTexture` 在 SDL3 上渲染正确，
稳态 0 次布局、draw 1.85 ms/帧。**在 SDL 后端上复现了与 raylib 相同的收敛性质** —— 这条比
「画面对了」更有意义，它说明收敛不是 raylib 路径的巧合。

## 四、当时不知道的三件事

1. **图集的 GPU 纹理不在进程 RSS 里。** 我一度把「4 条管线 × 1024² 图集 ≈ 40 MB」当成内存
   构成的主项；实测把默认起始尺寸改小 4 倍、RSS 只降 6 MB。原因是 Mesa 用 GEM 缓冲分配纹理，
   不进进程 RSS。后来 `malloc_trim(0)` 又把「页面构建 +21 MB」里的 19.2 MB 还了回来 ——
   那部分是分配器留住的临时对象，不是活对象。两次判断都被数字推翻。
2. **每帧 1277 次纹理绘制。** 文本路径是逐字形提交的（两个后端都是），这解释了 draw 成本里
   的固定部分，也是后续批处理的依据。
3. **设备实现不是纯头文件插件。** `IRenderDevice` 是 header-only，但 foundation 值类型有
   out-of-line 实现，独立设备必须链 `libnandina` 或编三个 foundation TU。我在第一次链接时
   才撞上这个（`undefined reference to NanRect::get_top()`），它直接进了 P4 的契约。

## 五、为什么现在敢说「替换生产后端」

两周前我的措辞是「探测记录，不是选型批准」。现在改口的依据不是感觉，而是四件可复跑的事：

- 真实页面在 SDL 后端上**正确渲染**，并且**收敛性质与生产后端一致**（不是画了个示例）；
- shader 链有固定的 host 工具、产物进构建图、坏产物能拦下（P1 门槛里最硬的几条）；
- 能力差异被列成了表，而不是「应该差不多」；
- 最小宿主证明 `NanWindow` 不是必须的，P4 的拆分有现实起点。

仍然没有证据的部分照样留着：Web 端没有一次有效的浏览器验收（截图停在加载壳上，分不清
「没加载完」和「没渲染」）、`SDL_shadercross` 的多后端产物一个都没构建过、键码映射没有经过
真实按键验证。这些是 P1/P2 的交付内容，不是「顺带做掉」的东西。
