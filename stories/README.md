# 开发故事

`docs/` 记录**项目现在是什么样**：契约、约束、API、路线图。
`stories/` 记录**它为什么变成这样**：哪条路走通过、哪条路撞了墙、当时在想什么、后来为什么改了主意。

这两件事需要分开写。契约文档必须简洁、确定、只描述当前事实；而决策过程里那些"我们原本以为 A，
结果发现 B"的部分如果塞进契约，会把它变成流水账。但它们又不该被丢掉——**下一个维护者最需要的
往往不是结论，而是"这个结论是怎么来的、当时排除了什么"**。

## 什么时候写一篇

- 一次方向性的调整（换了模型、删掉了某个 API、推翻了旧合约）；
- 一个查了很久才找到根因的问题；
- 一次"当时看起来对、后来证明是债"的取舍。

日常的加组件、修 bug 不需要写，提交信息就够。

## 怎么写

- **第一人称，允许写错**。故事的价值在于真实，不在于显得正确。把走过的弯路写出来，比
  只写结论有用得多。
- **具体**。带上文件、行号、提交号、当时的输出。可核对细节是故事和空谈的分界线。
- **写清楚"当时不知道什么"**。事后视角很容易把过程写成一帆风顺，那样就失去意义了。
- **不要复述 `docs/`**。结论请链接过去，故事只讲过程。

`NNN-短标题.md`，编号递增，不重编号。写完在下面加一行。
