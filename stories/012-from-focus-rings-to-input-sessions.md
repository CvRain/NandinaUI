# 从一个焦点环，讨论到输入会话的边界

> 2026-10-09，D1 设计讨论归档。**这是决策故事，不是实现完成报告。**
> 正式契约见 [统一输入、焦点与文本编辑](../docs/references/focus_and_input.md)。
> `2d49c56` 归档了第一版方向，本篇记录其后的审阅补全与最终取舍；没有把计划中的故障注入写成已通过测试。

## 一、先前修的是形状，接下来缺的是交互模型

[009](009-focus-ring-and-the-missing-input-modality.md) 的起点很具体：圆角按钮外面出现方框。
作者修好了几何，随后问“鼠标点击后为什么还一直留着环”。我最初倾向输入模态加一个关闭开关，
但作者把场景换成注册表单：有人鼠标逐个点，有人按 Tab，有人触摸，还有人用手柄。
触摸用户要不要唤起键盘？同一台设备的触屏、键盘和手柄又该怎么混用？

这让问题变了。它不再是给 painter 加一个条件，而是要回答三个不同问题：谁接收输入、
怎样让人知道目标、平台是否进入文字输入状态。若把三者压成一个 bool，后续例外会散进每个组件。

我们最终按指向定位、焦点导航、编辑输入区分意图，而不是永久按设备分类。
手柄可以模拟指针，也可以导航；鼠标点击按钮通常不需要持续提示，但点进输入框仍需要编辑提示。
因此查询不叫“是否画环”，而叫 `should_show_focus_hint()`；环只是主题可以选择的一种表现。

## 二、作者的七条审阅，把原则补成了可实现的规则

第一版 reference 已经写了“不重排”“按有意义交互”“程序化转移带原因”，但这些句子还不能
直接决定实现。作者逐项追问：谁标脏、滚轮算不算、没有历史怎么办、只读文本怎么办？

标脏讨论尤其有用。我同意纯提示只新增 paint，但后来发现只查节点的 semantics 位不够：
[`NanSceneTree::_transition_focus()`](../nandina/scene/scene_tree.cpp) 直接调用树级的
`mark_semantics_dirty()`。一个测试即使看到节点 semantics 位没置上，也可能漏掉语义快照重建。
于是验收必须先建立干净基线，再同时看节点脏位、树级 revision 和真实 focused 状态。

另一个小反例是“上下文变了，提示却没变”：输入框从键盘切到鼠标，按能力策略仍应显示提示。
我们最终要求按有效结果失效，而不是每次设备事件都标 paint；也不能为了 paint-only 清掉早先
合法的 layout 或 semantics 脏标记。

事件映射也从口号变成表格：移动、悬停、滚轮、单独修饰键不切换策略；Escape 的上下文必须
先于关闭回调，否则鼠标打开、键盘关闭的弹窗会按旧上下文恢复焦点。建立上下文不等于先导航，
否则 TextField 的光标和 Slider 的数值操作又会被全局焦点处理抢走。

## 三、“roving 都应该把焦点给子项”与当前代码不符

作者建议补 Tabs、DropdownMenu、RadioGroup 的验收。我赞成补，但检查后不能照搬一个模型：

- [`RadioGroup::move_focus()`](../nandina/widget/radio_group.cpp) 使用 focus-and-selection，
  会调用成员的 `request_focus()`。
- [`Tabs`](../nandina/widget/tabs.cpp) 和
  [`DropdownMenu`](../nandina/widget/dropdown_menu.cpp) 已有 selection-only 路径，
  容器保留真实输入焦点，内部活动项负责漫游。

如果规范写成“提示只能归真实聚焦子项”，就会在做 D1 时偷偷要求重写后两者。
我们改为要求提示清楚指向当前可操作项，并遵守各自已有的焦点/活动项模型；不存第二份活动项，
不让同一个方向事件又触发外层导航。委托绘制时也要使实际绘制位置失效，不能死守“只标焦点节点”。

## 四、第一帧隐藏的提案合理，但不是无损改进

作者提出：无交互历史时默认显示，会在启动自动聚焦按钮的第一帧让鼠标用户看到一个框。
不如默认隐藏，键盘用户第一次 Tab 自然会建立上下文，语义 focused 也没有丢失。

这个提案击中了最初的体验抱怨。我没有用“可访问性优先”一句话结束讨论，而是换了第一次输入：

```text
页面自动聚焦某个动作按钮
用户第一下按的是 Enter / Space，而不是 Tab
提示在按键分发时才变成显示，激活也在同一轮发生
```

这不是说激活一定错误，而是“按 Tab 就没损失”的论据没有覆盖这个用户。
在分发前切换提示状态，并不能保证人已经在动作前看到了绘制结果；保留语义 focused 也不等于
已经证明视觉和辅助技术两条路径都没有损失。

而且自动聚焦并非假想需求。检查
[`FocusScope::on_ready()`](../nandina/widget/internal/focus_scope.cpp) 和
[`NanRouter::restore_focus_after_navigation()`](../nandina/app/nan_router.cpp)，
都能找到挂载后聚焦的入口，代码没有“必须先收到一次输入”的前提。

最后作者接受保留**未知来源默认显示**，并要求把它写成明确的取舍。unknown 不能冒充 pointer；
明确的键盘流程也不能因此省掉上下文。是否该在普通页面启动时聚焦第一个动作按钮，留作单独的
初始聚焦策略问题，不通过隐藏提示来悄悄改变现有 Router 契约。

这次也顺手收紧了优先级：窗口活动是前置门槛，不是普通策略项。
“始终显示”只覆盖活动窗口里的模态隐藏，不会让失活窗口继续显示活动焦点提示。
逻辑焦点仍可保留，重新激活时再检查目标并计算提示。

## 五、平台服务的好先例，不能连同步假设一起复制

作者指出了现成的 [`IClipboard`](../nandina/scene/clipboard.hpp)：纯接口，由窗口注入 scene，
不暴露平台类型。我们因此确定文本输入服务也沿这条边界进入，暂名 `ITextInputService`。
这一步不需要先选 SDL、保留 raylib 还是新增独立平台适配。

但我不想把剪贴板的形状直接抄成几个方法就宣布完成。剪贴板读写可以同步，输入法会话有延迟回报：

```text
字段 A 开始组合输入 → 焦点转到 B → A 的旧组合事件才送达
```

如果只看“此刻聚焦谁”，A 的内容就会进入 B。清掉一个服务指针也挡不住已排队的回调。
所以正式方向同时记录了双向连接、会话身份/代次、先使旧投递失效再结束/解绑/释放的次序，
并禁止平台实现直接持有 widget 指针写值。连同一节点重新开始的会话，也必须区分新旧身份。

作者用“协议桩 / 平台组合实现 / 平台键盘实现”对应三种进度状态，作为解释很直观，但不适合
做成三个固定实现等级：一个实现可以支持多项能力，也可能能请求键盘却没有遮挡反馈。
因此我们最终分开四件事：

- 能力集合：支持什么；
- 每次请求结果：这次是否被接受、为什么失败；
- 平台实际状态：键盘是否可见、遮挡是否已知；
- 交付记录：这些行为在哪个平台被真实验证过。

模拟器完全可以模拟所有能力，却仍然不是实机证明。请求成功也不能伪造“键盘已经显示”。

## 六、D1 依赖的是平台能力，不是 D4 的全部迁移

作者核实了 app 尚无组合事件通路，EditableText 只有 composition 状态与操作接口。
这与 [005](005-the-animation-system-that-was-never-plugged-in.md) /
[006](006-the-animation-that-could-not-fire.md) 的教训相同：接口存在不等于生产消费者够得到。

但“现在没接通”还不能推出“必须换掉后端才能接通”。我们把依赖改成对应平台能力：
可以扩展现后端、增加独立平台适配，也可以使用 D4 新平台层；都通过同一个注入接口收口。
没有真实通路时，只能记录协议与模拟测试完成。组合输入和软键盘分别按平台验收，不能用一个
“阶段二完成”的勾选框替代。

## 七、这次交付到哪里为止

正式 reference 负责默认值、映射表、失效规则、注入边界和验收；本篇负责记录为什么没有采用
“启动默认隐藏”、为什么不把 roving 统一成子项真实焦点，以及为什么不能只复制剪贴板裸引用。

本次没有实现 `should_show_focus_hint()` 或 `ITextInputService`，没有跑新的输入实机测试，
也没有宣称三套构建再次通过。文档中的故障注入是后续实现必须证明的要求。
下一步仍是第一阶段：定形鼠标/键盘焦点 API、接入窗口激活状态并把提示真正接到组件绘制。
