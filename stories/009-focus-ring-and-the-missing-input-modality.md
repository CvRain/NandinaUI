# 焦点环：从"很丑"追到缺失的输入模态

> 历史记录：本文的几何修复和测试数值来自作者此前的工作区记录，相关代码不随本次文档提交；
> 本轮没有重新执行这些实验。D1 策略已定案但尚未实现，正式依据见
> [统一输入、焦点与文本编辑](../docs/references/focus_and_input.md)，后续讨论见
> [story 012](012-from-focus-rings-to-input-sessions.md)。下文保留当时的判断，并标注被取代的结论。

作者说按钮和 Badge/Chip 获得焦点后外面套的方框很丑，想取消。我按"先核实再动手"走了一遍，
结果这件事分成了两层：**一层是我能修的绘制错误，另一层是真需要讨论的设计问题**。

## 一、先确认这不是审美问题

`BoxPainter::paint_outline`（控件自己的边框）早就在用圆角描边，注释写着理由：

```cpp
/// 圆角 > 0 时用圆角描边，避免方框边角与圆角填充之间留白（如勾选框的四个角落）。
```

而 `FocusRingPainter::paint` 一直在用 `draw_rect_outline`。**14 个控件共用这一个 painter**，
所以不是"某个组件没对齐"，是这一条绘制路径从没跟上圆角。

环画在控件外侧一圈，半径必须跟着外扩同样的量才同心：

```cpp
const auto expansion = ctx.logical_to_screen(ring.width + gap);
if (corner_radius > 0.0F) {
    ctx.device().draw_rounded_rect_outline(
        expanded, ctx.logical_to_screen(corner_radius) + expansion, thickness, color);
}
```

`corner_radius` 我刻意**不给默认值**：有默认值，圆角控件就会悄悄退回方框，也就是这次的
bug；现在编译器逼着 14 个调用点各自表态在给什么形状描边（Switch 描的是轨道、AlertDismissButton
是圆、BreadcrumbLink 是唯一故意保持方框的）。

## 二、为什么这个错误能活这么久

`tests/button_tests.cpp` 的录制设备**没有覆写** `draw_rounded_rect_outline`。接口给它留了
回退实现（内部转调 `draw_rect_outline`），注释写着"测试设备可不实现"。于是：

- 控件边框和焦点环都记成 `rounded = false`；
- `RectCall::rounded` 这个字段**永远是 false**，测试里没有任何断言能区分圆角和方框。

换句话说，测试设备对"形状"是瞎的，所以这条路径上的一切形状回归都测不出来。修的时候顺手
给它补上覆写，并加了两条会红的断言：painter 层（半径 = 12 + 外扩 6，注入方框后实测 12）与
组件层（聚焦的 Button 必须画**圆角**描边，半径 = 容器圆角 + 环宽 + gap）。

## 三、修完才看清的真问题：环该不该有

作者的理由很实在：

> 按钮被点下后有了其他更强的视觉停留表现，已经可以突出焦点位置了。但是如果按钮是点击一下
> 回弹的，看不出来到底是否点击过了，而且也不知道焦点在哪里，则可能考虑需要这个内容。

这观察在**鼠标路径**上是对的，但它把**焦点**和**选中/当前**混在一起了。用作者自己的侧边栏
就能证伪：

```text
按 Tab：焦点从「首页」移到「锚点」
        treatment 绑的是 current_page，没变 → 「首页」仍然是 filled
        → 除了焦点环，屏幕上没有任何东西告诉你焦点在「锚点」
```

也就是说：鼠标点击时两者恰好重合（点了哪个哪个就变 filled），Tab 导航时**不重合**。
"点击回弹"的按钮就是后者，作者自己也点了出来。

我当时把结论简化成了“鼠标路径上多余，键盘聚焦才显示”。这句话后来被证明过宽：
指向聚焦的可编辑字段也需要明确提示，不能用“模仿 focus-visible”替代完整的目标能力与交互策略。

## 四、代价与现状

当时检查的框架代码**没有输入模态跟踪**（当时搜索 `modality` / `focus_visible` / `last_input` 无匹配；后续文档引用这些名字不算实现）。
`set_focus()` 同时被两条路调用 —— `Pressable` 在点击时、`focus_next/previous` 在按键时 ——
但没有记录是谁调的。要做 focus-visible 需要：给 `set_focus` 加来源、树里存最近模态、再给那
14 个画环的地方一个 `focus_visible()` 查询。这是当时的草图，最终命名是
`should_show_focus_hint()`，并且不再把“最近设备”作为唯一决策依据。

我本来想直接在应用里驱动一次真实焦点来截张图验证，`request_focus()` 没生效（原因未查明，
怀疑与窗口未激活有关），最后是临时把绘制条件放开才看清形状 —— **焦点机制本身没有被这轮验证**，
它由单测覆盖（`tree.set_focus` → 画出圆角环）。

## 五、留下的决定

我当时的建议是"focus-visible 打底 + 实例级 `.focus_ring(false)` 逃生门"。**这个建议后来被
推翻了**：作者把它展开成了 [统一输入、焦点与文本编辑](../docs/references/focus_and_input.md)，
改成按**交互意图**（指向定位 / 焦点导航 / 编辑输入）而不是按设备决定呈现策略，并且明确
第一阶段**不**增加通用 `.focus_ring(false)`。

我那份建议有两处是错的，记在这里免得再犯：一是"鼠标聚焦一律不显示"会误伤**可编辑输入框**
（它由指向聚焦时也必须给出编辑提示）；二是把触摸/手柄按设备归入 pointer —— 同一设备既能指向
也能导航，设备不该被永久绑定到一种策略。
