# 资源自动构建之前，先找回查询丢掉的作用域

> 2026-10-11，D5 讨论归档。设计已冻结，运行时与构建拆分尚未实施。
> 正式契约见 [资源构建、部署与运行时定位](../docs/references/resource_build_and_deployment.md)。
> 本篇记录推翻过的判断；未来验收要求不等于本轮已通过测试。

## 起点是多跑了一次命令

作者希望引入框架、声明资源后，就能正常构建运行，而不是先编框架取得 nanres，再手工打包。
SQLite 已由 wrap 改为 vendored，格式门禁也固定到了 clang-format 23.1.1。此时很容易把下一步
理解成搬目录、增加 custom target，或者先换一个更轻的包格式。

我检查后发现，项目已有 IResourceBackend、四类后端和构建 helper；真正缺的是独立构建边界、
应用目标依赖，以及部署后的定位规则。SQLite 已是独立 static_library，每个构建配置编译一次，
不是每个消费 target 各编一次。关运行时后端却保留打包工具，也不意味着能省掉 SQLite 编译。

第一版计划又走得太远：把身份决策放到解耦之前。作者指出，搬实现、去掉完整 UI 依赖和增加
关闭组合，并不依赖 ID 如何生成。这让首批重新变小：保留行为，先证明构建目标真的分开。

## 内容相同，不等于同一条资源记录

随后讨论出现一个看起来简洁的方案：key 是作者身份，ID 就用内容摘要。但当前包用 ID 作记录
主键，记录各自持有 key 和 media_type。同一图标放在两个 key 下，字节完全相同也仍是两条记录；
直接拿纯字节摘要当主键，会在没有哈希碰撞的情况下发生冲突。

另一个证据在 [FontLoader](../nandina/text/font_loader.cpp)：缓存取 ResourceId 和 face index，
没有挂载作用域。因此“只要求包内唯一”不能直接套到当前跨挂载消费者。我们没有为此拆 blob 表，
而是把记录身份、内容摘要、运行时缓存身份分开，保留包格式，先修运行时查询。

## 换成 handle，信息仍然不存在

作者最初建议缓存改用 ResourceHandle。继续往下读才发现，它只是 shared_ptr<const Resource>，
Resource 中没有挂载字段，查询结果也没有。manager 明明有 MountId，却在遍历后端时只把命中的
资源返回了。缓存层无法补回一个从未收到的信息。

作用域于是移到管理器的解析边界。但不能直接让所有 ResourceLookup 都带 MountId：这个别名
也是 IResourceBackend::find 的返回类型，同一 backend 可以挂多次，它不知道本次 manager 域。
最终分工是后端给本地结果与发布代次，manager 包装域身份和挂载身份；find、require、流的 key/ID
八个入口一起迁移。只改 find 然后由 require 返回裸句柄，会把信息再丢一次。

返回作用域也不能解决输入歧义。裸 ID 在多个挂载命中时，返回“我选中了谁”并不证明选对。
所以 key 保留优先级覆盖；ID 单一命中继续成功，多重命中明确报歧义。这个行为变化属于作用域批，
不能偷偷放进承诺逻辑等价的解耦批。

## 两个生命周期判断还需要再纠正

“卸载后旧句柄必须失败”说得过头。已经物化的不可变字节可以继续使用，旧引用重新解析才需要
拒绝。否则已加载字体和图片会因卸载无端失效。mount 接受 shared_ptr 也不能证明流已经保活后端，
必须检查流实际持有什么。

最后一次审阅又出现了一个具体误读：只看
[file_resource_stream.hpp](../nandina/resource/file_resource_stream.hpp) 的 path 和 declared_size，
就判断文件流没有保持打开。实际 [.cpp](../nandina/resource/file_resource_stream.cpp) 中的
FileResourceStream 持有 std::ifstream，read/seek 都消费它。不过，打开文件与不可变快照仍是
不同保证，外部原地修改或截断不受这个所有权阻止。

弱域令牌也需要限定。按控制块所有权比较可以避免裸地址复用和多个 manager 的 MountId=1
发生混淆；但 expired 令牌不能全部当成同一个空指针。清扫死域只能处理 manager 已销毁的情况，
活着的 manager 中旧挂载和旧代次还得清理。计数器变化避免错误复用，不会自动完成缓存回收。

## 三批，各自证明不同的事

最终边界是解耦不改语义，作用域改查询和缓存但不改格式，身份另定生成算法。身份设计可以与
解耦并行，不意味着一个提交要混进两条工作线。

解耦验收固定清单、源文件与既有 lock，在两个独立输出根比较前后逻辑资源集合；先查重复 key，
再排序比较内容、既有 ID、别名与存储语义。新增随机 ID 的具体值不加入等价要求。两个根也不自动
证明并行安全，仍需真正同时构建的用例。作用域批另测跨挂载冲突、发布代次、别名、旧引用和流。

这轮没有执行这些未来测试，也没有完成 nanres 拆分。留下的实施依据已经能够区分：哪些证据
证明现状，哪些契约需要改代码，哪些验收只能在下一批真正运行后才算成立。
