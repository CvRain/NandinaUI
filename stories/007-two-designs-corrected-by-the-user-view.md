# 007 · 两次被"用户视角"纠正的设计

> 2026 年 10 月，紧接 [006](006-the-animation-that-could-not-fire.md)。
> 起因是一轮使用反馈：六条抱怨加一条"想给文字加下划线但很难做"。
> 结果不是修六个 bug，而是**两次推翻我自己的设计框架** —— 而且两次都是被同一个角度纠正的。
> 状态：决定已归档到 [节点表现层](../docs/references/node_presentation.md) 与
> [配置与开发体验](../docs/references/authoring_configuration.md)；代码尚未动。

## 一、七条抱怨，第一次分类

作者的原话散成七条，我先把它们核实了一遍（能核实的都核实了）：

| # | 抱怨 | 核实结果 |
| --- | --- | --- |
| 1 | `on_enter` / `on_hover` 类回调 `&` 捕获会崩 | ✅ `guarded()` 只查作用域令牌，**不管捕获** |
| 2 | `Label` / `Button` 缺基础配置函数 | ✅ `Label` 只声明了 `set_color_token`，其余靠公有继承 `primitives::Text` |
| 3 | 字号被三处写，到底谁赢 | ✅ `font_size_explicit_` 粘性标志 + 值上"最后写赢" |
| 4 | 悬浮动画卡得像 PPT | ✅ 根因在下面第三节——比"重排"更深一层 |
| 5 | `padding` 没有 margin，四方向不方便 | ✅ 盒子模型缺口 |
| 6 | 回调参数查不到该塞什么 | ✅ 模板 + `Handler` 占位符 |
| 7 | 想给文字加下划线，很难且会打破约束 | ✅ 缺"不触发重排的绘制属性" |

**七条里有五条指向同一个东西**：节点的可定位 / 可动画表面太窄。所以正确的动作不是
修七个点，而是补那一层。这个判断后来被证明是对的，但我最初补它的方式错了（第四节）。

## 二、第 4 条：卡顿不是掉帧，是每帧在光栅化

我第一版结论是"字号动画每帧触发重排"，写进回复里就交差了。再往下看一层才发现更狠：

```text
set_font_size → update_metrics()  →  重新整形文本
             →  字号是新的  →  字形图集按 (字形, 字号) 缓存  →  重新栅格化
```

14→18px 的补间意味着**几百个互不相同的字号**，每个都要栅格化一遍。所以"PPT 感"的
真实代价是**每帧做一次字体光栅化**，不是掉帧。

由此得到全篇的骨架——**属性代价分级**：

| 级别 | 属性 | 代价 |
| --- | --- | --- |
| L1 绘制 | color / border / radius | 重绘该节点 |
| L2 变换 | opacity / translate / scale | 重绘（合成变换） |
| L3 布局 | width / height / **font_size** / padding / gap | **重排子树** |
| L4 整形 | font_size | 重排 **+ 按字号重新栅格化字形** |

而这件事最刺眼的地方是：**同一个项目里已经有正确答案**。侧边栏的注释写着"它是纯绘制
属性（`DirtyFlags::paint`），不会触发重排" —— 所以 sidebar 选 `radius`（免费），
home_page 选 `font_size`（昂贵）。我在 006 里"修好"了 home_page，却把这条昂贵的选择
**保留了下来**。它是 006 的遗漏，不是新发现。

## 三、第 7 条：从"加个下划线"到"缺一套图形出口"

我的第一反应是"给 `visual::Path` 加一条 opacity，下划线就能淡入"。作者把问题推大了
一层：**不是缺下划线，是缺图形绘制的出口。**

核实之后他说得对，而且缺口的位置很具体：

| 层 | 现状 |
| --- | --- |
| 设备层 | 够用：rect / rounded rect(+outline) / circle / arc / line / 阴影 / 文字 |
| 中间层 | **已经有 painter 家族**：box / arc / focus_ring / ripple / shadow |
| 顶层 | **零个形状节点**（全仓搜 `class Rectangle / Circle / Shape` 无匹配） |

所以要做的是**把已有能力接出来**：公开 painter 入口（给自定义 `on_draw`，下划线走这条）
+ 形状节点家族（参与锚定/布局、可主题、可动画）。

作者另外给了一条克制原则：**多边形不做**，理由是"空想问题不可靠，用到再列"。
这条被采纳并写进了非目标。

## 四、第一次被纠正：anchors 不是装饰，是第二套布局

我写了一份设计文档，把 anchors 定位成"layout 的补充"—— 一个挂在子项上的属性包，
用来给个别子项钉位置（下划线就是例子），规则是"锚定的子项脱离排列流"。

**作者纠正**（大意）：

> 对**设计者**来说 anchor 是"给子组件外挂父属性"的工具，但对**开发者**这就是另一个
> 布局系统。只有 layout 时，开发者的思路是盒子模型层层包裹层层递进；有了 anchors 就不是
> 了 —— 开发者会很自然地用它描述大方向的定位关系，内部再混 layout。最简单的例子：
> 侧边栏可以缩放、可以从左侧移到右侧，用 anchor 很简单（改锚点），用 layout 就麻烦一点。

**这是两套世界观。** 我写的是"框架设计者视角"（什么容易加进去），他说的是"使用模型"
（这东西会怎么改变我写代码的方式）。差别落在最深的那一层：

```text
只有 layout：  结构 == 排列。树的形状就是 UI 的形状。
有 anchors：   结构 != 排列。可以是扁平的树，空间关系由"谁贴着谁"表达。
```

**树不再是布局。** 我原来的文档完全没有这一条，而它是枢纽 —— 它连带解释了为什么需要
显式 z 序（绘制顺序不能再从树上推）、为什么必须有兄弟锚定。

作者给的 markdown 编辑器例子（侧边栏 + 编辑栏 + 预览，内部再各自用 Column / Row）直接
成了验收用例，因为它能证明"树 ≠ 布局"。

**这次纠正连带推翻了我文档里的四条**，其中一条是明确的错：

- **兄弟锚定从"非目标"改为 v1 必需** —— 没有 `editor.left = sidebar.right` 就表达不出
  "内容区占掉剩余空间"。我按装饰视角把它省了，按布局视角它是核心；
- 需要**隐式尺寸 → 依赖序 → 环检测**的求解顺序；
- 需要**显式 z 序**；
- "同一层混用"要写成明确的非目标，改成**逐层治理**（一个容器对直接子项只用一套）。

还有一句提纲挈领的话，我原来的框架完全反了：

> **QML 是以 anchor 为主、layout 为辅的。**

## 五、第二次被纠正：`requires` 说不清"该填什么"

第 6 条我建议"用 `static_assert` 把错误信息写得人能看懂"。作者直接指出这没用：

> `require` 只能告诉你填这个参数是错误的，但没办法告诉你填什么是正确的；而且因为用了
> 模板，用户也不知道 `Handler` 是个什么东西。

他是对的。`requires` 只能证明"不合法"，说不出"合法的是什么"；`Handler` 是个占位符，
用户连"该传回调"都读不出来。

**他给的方向比我好**：换 `std::function` 是亏的，`Handler` 是资产；用 **concept 判断
哪些 handler 能被 PointerArea / GestureArea 接受**，签名集合是有限的
（`[](const MouseEnterEvent&)`、`[](const MouseButtonEvent&)`、`[](){}` …），可以用
**模板特化**表达；用户想要别的形状就自己扩展；再用 `Handler` 兜底。

我在这个方向上补了四点：

1. **先分两类**：立刻调用（`.configure`）vs 存起来以后调用（`on_*` / `bind` / `computed`）。
   前者可以用 **`std::function_ref`（C++26）** —— 具名签名出现在错误里，却零分配、
   间接最小。这是"可发现性"与"效率"之间被忽略的中间点；
2. **concept 该判断"接受哪个事件"**，然后入口用一次 `if constexpr` 派发 ——
   比写 N 个特化省，效果一样，而且"接受哪些签名"只有一处声明，**那一处就是文档**；
3. **兜底的是派发点，不是 concept**：给一个 `HandlerDispatch` trait 让用户特化；
4. **诊断分层**：concept 注释（写的时候）→ `= delete("理由")`（C++26）→ contracts →
   `static_assert` 只用在最后一道兜底。这时它才有信息量。

## 六、第 1 条：`guarded()` 的假安全感

```cpp
return [lifetime = callback_lifetime_, handler = ...](auto&&... args) mutable {
    if (lifetime.has_value() && lifetime->expired()) { return; }  // 只查作用域令牌
    std::invoke(handler, ...);                                    // 然后照常解引用捕获
};
```

`guarded()` 保证的是"宿主作用域还活着"，**完全不检查 handler 捕获了什么**。所以
`[&local]` 照样悬垂，崩溃发生在 `std::invoke` 内部 —— 令牌检查救不了。

它制造的是**假安全感**：builder 替你包了一层，看起来生命周期被兜住了。这和 006 里
那个"测试写对了、产品代码偏离了"是同一种失败模式 —— **保护存在，但保护的不是这件事故**。

## 七、第 2、3 条：不改变行为，把规则写下来

- **第 2 条**（`Label` 只声明 `set_color_token`，其余靠公有继承 `primitives::Text`）：
  不是缺函数，是**查不到**，而且与契约第 9 节"primitive 不应成为入门依赖"冲突。
  决定：组件必须**显式声明自己承诺的配置入口**，"DSL 能表达的在组件上也必须可查"。
- **第 3 条**（字号谁赢）：机制是**粘性标志 + 最后写赢**。检查了反向方案（让
  `set_style` 也置标记）—— 那会让组件应用配方时把自己标成"显式"、从而封死后续的主题
  应用，是更坏的错误。所以**保留行为，把规则写成两条**：`set_style` 是批量派生来源、
  不置标记；单字段 setter 是实例显式意图、置标记并从此赢过派生来源。

  顺带记下一个必须写进文档的坑：标记的含义是"**有过**实例级显式设置"，而不是
  "当前值是显式的" —— 所以 `set_style` 之后标记状态不变，这是最容易被当成 bug 的地方。

## 八、第 5 条：盒子模型

`padding`（容器内侧）+ `gap`（排列流子项间）已有，缺**子项 margin** 与四方向 padding。
`NanInsets` 看起来已是四分量结构，所以"四方向"**可能只是 DSL 没暴露**（这一点我标了
"待确认"，没有替你断言）。另外它和锚点是一块拼图：锚点的 `left/right` 本身就是 CSS
意义上的 margin，所以两件事应该一起收尾。

## 九、这一轮真正学到的东西

**我两次把"容易实现"当成了"设计对不对"的标准。**

- anchors：我按"钉住一个子项"这个小实现来判断它的价值，于是把它降级成装饰；
- DX：我按"加一句 static_assert 很便宜"来判断可发现性，于是绕过了"用户根本不知道参数
  是什么类型"这个真问题。

两次的纠正者都是**使用者视角**：这东西会怎么改变我写代码的方式。这和 005 里作者自己
那条教训是同一个形状 —— 他当时按"哪个看起来更高级"选了弹簧，而不是按"哪个量级需要"。

所以值得写成一条评审问题：

> **这个改动的价值，是按"我多容易加进去"算的，还是按"它会怎么改变使用者写代码的方式"算的？**

另外两条：

- **失效的功能会掩盖它周围的悬垂访问**（006）。这一轮又见到同类：`guarded()` 让"捕获
  悬垂"看起来被兜住了。
- **框架造好了能力，却没给消费者把手**（005 的 `Group`、第 7 条的 painter 家族、
  `NanNode2D::set_local_opacity` 存在却不可动画）。三次都是同一个形状。所以每造一个
  机制都该问：**预期消费者是谁，他够得到吗？**
